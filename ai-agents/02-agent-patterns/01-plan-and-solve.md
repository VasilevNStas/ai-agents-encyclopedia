# Урок 4: Plan-and-Solve — стратегия + тактика

> [!quote] Ключевая идея
> ReAct хорош в тактике («что делать на этом шаге»), но плох в стратегии («какой общий план из 10 шагов»). Plan-and-Solve (Wang et al., 2023) добавляет **фазу планирования** перед циклом действий.

---

## Проблема ReAct

ReAct идёт шаг за шагом без общего плана:

```
Thought: Надо найти файл config.py
Action: grep config.py
Obs: found

Thought: Теперь прочитать его
Action: read config.py
Obs: там переменная DB_HOST

Thought: Надо проверить, используется ли она в main.py
... и так далее, шаг за шагом, без карты
```

**Проблема:** агент не знает, сколько всего шагов, где он сейчас, и не отклоняется ли от курса. Он может зациклиться или уйти не туда.

---

## Как работает Plan-and-Solve

Два этапа:

```
ФАЗА 1: PLAN
──────────────
LLM составляет пошаговый план на основе задачи.

ФАЗА 2: SOLVE
──────────────
LLM выполняет план шаг за шагом (как ReAct),
но с возможностью скорректировать план по ходу.
```

```python
def plan_and_solve(task: str, max_steps=20):
    # ФАЗА 1: План
    plan_prompt = f"""
    Составь детальный план для задачи: {task}
    
    Формат плана:
    1. <шаг> — <что сделать>
    2. <шаг> — <что сделать>
    ...
    
    Учти: если на каком-то шаге обнаружится,
    что план неверен — скорректируй его.
    """
    
    plan = llm.generate(plan_prompt)
    
    # ФАЗА 2: Выполнение
    context = f"План:\n{plan}\n\nВыполнение:\n"
    
    for step in range(max_steps):
        response = llm.generate(context, tools=TOOLS)
        
        if response.has_tool_call():
            result = execute_tool(response.tool_call)
            context += f"Шаг {step + 1}: {response.thought}\n"
            context += f"Action: {response.tool_call}\n"
            context += f"Obs: {result}\n"
        else:
            # Проверка: план выполнен?
            if "FINAL" in response.content:
                return response.content
            
            # Может, пора скорректировать план?
            context += response.content
    
    return "Max steps reached"
```

## Plan-and-Solve vs ReAct

| Критерий | ReAct | Plan-and-Solve |
|----------|-------|---------------|
| Стратегия | Нет | Есть (план в начале) |
| Тактика | Есть | Есть |
| Коррекция плана | Нет (нет плана) | Да (может перепланировать) |
| Расход токенов | Меньше | Больше (план + выполнение) |
| Предсказуемость | Низкая | Высокая |
| Сложные задачи | Плохо | Хорошо |
| Простые задачи | Хорошо | Избыточно |

> [!important] Когда что использовать
> - **ReAct**: задачи на 2-5 шагов, исследовательские, exploratory
> - **Plan-and-Solve**: задачи на 10+ шагов, где важен порядок

## Пример: деплой приложения

План, который составляет агент:

```
ПЛАН деплоя:
1. Собрать проект (npm run build)
2. Проверить, что сборка без ошибок
3. Запустить тесты
4. Если тесты проходят — загрузить на сервер
5. Перезапустить сервис
6. Проверить health-check
7. Если health-check упал — откатить
```

Без плана ReAct мог бы: собрать → загрузить → перезапустить → ... и только потом заметить, что тесты не запускал. С планом — каждый шаг проверяется относительно общего замысла.

## Динамическое перепланирование

Сила Plan-and-Solve не просто в плане, а в том, что агент может **изменить план** по ходу:

```
ШАГ 3: запуск тестов
  Obs: тесты падают — в config.py ошибка

Агент не продолжает слепо, а перепланирует:
  → Новый план: починить config.py → пересобрать → снова тесты → деплой
```

Реализация:

```python
def replan_if_needed(context: str, plan: str, step: int) -> str:
    """Спрашиваем LLM: план всё ещё актуален?"""
    
    check = llm.generate(f"""
    Текущий план: {plan}
    Выполнено шагов: {step}
    Текущий контекст: {context}
    
    Вопросы:
    1. План всё ещё корректен?
    2. Нужно ли изменить порядок шагов?
    3. Нужно ли добавить/удалить шаги?
    
    Если план корректен — ответь "OK".
    Если нет — напиши новый план.
    """)
    
    if check != "OK":
        return check  # новый план
    return plan  # план корректен
```

## Разбор реального кейса

На практике Plan-and-Solve выглядит как гибрид:

```python
class PlanAndSolveAgent:
    def __init__(self, tools: list):
        self.tools = tools
        self.plan = []
        self.step_index = 0
        self.context = []
    
    def plan_phase(self, task: str):
        prompt = f"""
        Задача: {task}
        
        Составь план. Каждый пункт — это вызов
        одного инструмента или проверка.
        
        Формат:
        STEP 1: <инструмент> — <цель>
        STEP 2: <инструмент> — <цель>
        ...
        """
        self.plan = self._parse_plan(llm.generate(prompt))
    
    def solve_phase(self, task: str):
        for i, step in enumerate(self.plan):
            result = self._execute_step(step)
            
            # После каждого шага — проверка плана
            if self._should_replan(result):
                new_plan = self._replan(task)
                if new_plan:
                    self.plan = new_plan
                    break
            
            self.step_index = i
    
    def run(self, task: str):
        self.plan_phase(task)
        return self.solve_phase(task)
```

## Провальный сценарий (Anti-pattern)

**Когда Plan-and-Solve ломается:**

1. **Слишком абстрактный план** — «решить задачу» не является планом. План должен быть конкретным: «найти файл X → прочитать → изменить Y → проверить»
2. **Жёсткий план без перепланирования** — если агент никогда не пересматривает план, он ничем не лучше Plan→Execute
3. **План в голове, а не в контексте** — если план не записан в сообщениях, модель его «забудет» через 2-3 шага

---

## Резюме

```
ReAct         = думай → делай → думай → делай (без карты)
Plan-and-Solve = составь карту → иди по карте → сверяйся с картой
```

**Плюсы:** стратегическое мышление, предсказуемость, масштабируется на сложные задачи  
**Минусы:** дороже ReAct, избыточен для простых задач, требует хорошего промпта для фазы планирования
