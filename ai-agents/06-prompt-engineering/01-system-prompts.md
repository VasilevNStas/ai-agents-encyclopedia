# Урок 21: System Prompt — конституция агента

> [!quote] Ключевая идея
> System prompt — это **не просто инструкция**, а конституция агента. Она определяет его личность, правила поведения и границы дозволенного. Хороший system prompt — половина успеха агента.

---

## Анатомия промпта

Каждый промпт состоит из шести элементов (RCTFCE):

| Элемент | Описание | Пример |
|---------|----------|--------|
| **Role** | Кто ты | «Ты — опытный Python-разработчик» |
| **Context** | Что известно | «Пользователь описал баг в auth.py» |
| **Task** | Что сделать | «Найди и исправь ошибку» |
| **Format** | Формат ответа | «Ответь JSON: {"file": "...", "fix": "..."}» |
| **Constraints** | Ограничения | «Не используй сторонние библиотеки» |
| **Examples** | Примеры (few-shot) | «Вот пример правильного ответа: ...» |

```python
def build_prompt(role, context, task, format, constraints, examples=None):
    prompt = f"{role}\n\n{context}\n\n{task}\n\n{format}\n\n{constraints}"
    if examples:
        prompt += f"\n\nПримеры:\n{examples}"
    return prompt
```

## Правила хорошего system prompt

### 1. Императивность
```
❌ "Пожалуйста, не могли бы вы, если вам не сложно, проверить этот код?"
✅ "Проверь код на уязвимости. Найди все уязвимости. Сообщи о каждой."
```

### 2. Позитивные инструкции вместо негативных
```
❌ "НЕ используй eval. НЕ пиши комментарии. НЕ удаляй файлы."
✅ "Используй ast.literal_eval. Пиши самодокументируемый код без комментариев.
    Работай только с read-only инструментами."
```

### 3. Приоритет: важное в начало и конец
Из-за lost-in-the-middle эффекта:
```
[sys prompt: важное] [контекст задачи] [детали] [sys prompt: важное]
```

### 4. Краткость
- System prompt < 2000 токенов
- Если длиннее — разбей на несколько сообщений
- Каждое слово должно быть нагружено смыслом

## Шаблон system prompt для агента

```markdown
# Role
Ты — опытный инженер по отладке кода.
Ты работаешь в консоли и используешь инструменты.

# Context
Задача: найти и исправить баг в модуле авторизации.
Файлы проекта: /project/src/auth/

# Task
1. Найди файлы, где происходит авторизация
2. Прочитай их и найди логические ошибки
3. Исправь найденные ошибки
4. Проверь, что исправления не сломали тесты

# Format
Ответь кратко: что нашёл, что исправил.
Если ничего не нашёл — скажи "багов не найдено".

# Constraints
- НЕ изменяй файлы, не связанные с авторизацией
- НЕ используй eval или exec
- Если сомневаешься — спроси пользователя
- Каждое изменение подтверждай перед выполнением
```

## Примеры: плохой vs хороший

```python
# ❌ Плохой system prompt
system_prompt = "Ты — ассистент. Помоги пользователю."

# Агент делает что хочет, как хочет — хаос
```

```python
# ✅ Хороший system prompt
SYSTEM_PROMPT = """
Ты — агент для рефакторинга кода.

ПРАВИЛА:
1. Всегда читай файл перед изменением
2. Не изменяй больше 1 файла за раз
3. После каждого изменения — проверь синтаксис (python3 -m py_compile)
4. Если тесты не проходят — откати изменения
5. Работай ТОЛЬКО в директории /project/src

ИНСТРУМЕНТЫ:
- read(path) — прочитать файл
- edit(path, old, new) — заменить текст
- run(command) — выполнить команду
- test() — запустить тесты
"""
```

## Ошибки при написании

1. **Слишком длинный** — >2000 токенов, модель теряет фокус
2. **Слишком абстрактный** — «будь полезным» не говорит агенту, что делать
3. **Противоречия** — «будь креативным, но строго следуй правилам» ≠ работает
4. **Нет приоритетов** — всё перечислено списком без ранжирования
5. **Нет указания формата** — модель отвечает «как бог на душу положит»

## Decision Tree — как собрать system prompt

```
Есть задача для агента?
  │
  ▼
Определи Role:
  Кто должен это делать?
  «Ты — senior Python-разработчик»
  «Ты — исследователь данных»
  «Ты — технический писатель»
  │
  ▼
Определи Task:
  Что конкретно сделать?
  «Найди баг в auth.py и исправь его»
  НЕ «помоги с кодом», НЕ «будь полезным»
  │
  ▼
Нужен специфический формат ответа?
  ├── Да → Format: JSON-схема
  └── Нет → Format: markdown / краткий ответ
  │
  ▼
Есть ограничения?
  ├── Не делать: «не используй eval», «не меняй чужие файлы»
  └── Делать вместо: «используй ast.literal_eval», «работай только в src/»
  │
  ▼
Task сложная (> 3 шагов)?
  ├── Да → Context: передай контекст задачи
  └── Нет → Context: можно пропустить
  │
  ▼
Формат нестандартный?
  ├── Да → Examples: 1-3 примера
  └── Нет → Examples: не нужны
  │
  ▼
Готово. Проверь размер (< 2000 токенов) и императивность.
```

## Анализ реального system prompt — строка за строкой

Разберём `AGENTS.md` из этого проекта (он же — system prompt для профессора):

```markdown
AGENTS.md:
  Роль: Профессор и Наставник
  Контекст: курс по AI-агентам, Май 2026
  Задача: провести студента от нуля до Архитектора
  Метод: сократовский диалог, вопрос → ответ → уточнение
  Skills: загружать по необходимости
```

**Почему это работает:**
1. **Role** (`Профессор`) задаёт авторитет — модель не сваливается в «дружеский чат»
2. **Context** (`Май 2026, курс по AI-агентам`) — хронологическая привязка, чтобы оперировать актуальными техниками
3. **Task** (`провести от нуля до Архитектора`) — измеримая цель, есть критерии (10 пунктов)
4. **Краткость** (888 токенов) — модель не «забывает» свою роль к середине диалога
5. **Skills** (`prompt-engineer`, `agent-architect`) — подгружаются по запросу, не засоряют контекст

## Антипаттерны — разбор на реальных примерах

### 1. Слишком абстрактная роль
```markdown
❌ «Ты — полезный ассистент. Помоги пользователю.»
→ Модель не знает, в чём её специализация.
→ Отвечает средне по всем темам.

✅ «Ты — senior DevOps инженер.
   Специализация: Kubernetes, Docker, CI/CD.»
→ Модель отвечает как эксперт.
→ Если спросить про кулинарию — скажет «это вне моей компетенции».
```

### 2. Смешение задач
```markdown
❌ «Напиши код и проверь его на уязвимости и задокументируй.»
→ Модель делает всё сразу и плохо.

✅ «Сначала напиши код. Потом я скажу, что проверять.»
→ Два отдельных промпта = два качественных результата.
```

### 3. Противоречия
```markdown
❌ «Будь креативным, но строго следуй правилам.»
→ Креативность ≠ следование правилам.
→ Модель не знает, что важнее.

✅ «Сначала предложи 3 креативных идеи без ограничений.
   Потом выбери лучшую и реализуй по стандартам проекта.»
→ Два шага = два режима.
```
