# Глоссарий — все термины курса

## Модуль 1: Фундамент

| Термин | Определение | Урок |
|--------|-------------|------|
| **LLM** | Large Language Model. Модель, предсказывающая следующий токен. | 1 |
| **Token** | Единица текста, которую видит LLM (слово/часть слова/знак). | 1 |
| **Attention** | Механизм, позволяющий токенам «смотреть» на другие токены в контексте. | 1 |
| **Context window** | Количество токенов, которое модель может «видеть» одновременно. | 1 |
| **Temperature** | Параметр sampling: чем выше, тем креативнее ответ. | 1 |
| **Sampling** | Стратегия выбора следующего токена (greedy, top-k, top-p). | 1 |
| **Stateless** | Свойство LLM: каждый запрос — чистый лист, нет встроенной памяти. | 1 |
| **Agent** | Система, в которой LLM используется как ядро принятия решений в цикле. | 2 |
| **System prompt** | «Конституция» агента: Role, Context, Task, Format, Constraints. | 2 |
| **Tool** | Инструмент, через который агент взаимодействует с внешним миром. | 2 |
| **Agent Loop** | Базовый цикл: LLM → решение → действие → наблюдение → повтор. | 2 |
| **Autonomy level** | Степень автономности агента: 0 (Copilot) → 4 (Autopilot). | 2 |
| **ReAct** | Паттерн: Reasoning + Acting — чередование рассуждения и действий. | 3 |
| **Thought** | Рассуждение агента «вслух» (почему он делает то, что делает). | 3 |
| **Action** | Конкретный вызов инструмента от имени агента. | 3 |
| **Observation** | Результат выполнения инструмента. | 3 |

## Модуль 2: Паттерны агентов

| Термин | Определение | Урок |
|--------|-------------|------|
| **Plan-and-Solve** | Паттерн: сначала составить план, потом выполнять с возможностью корректировки. | 4 |
| **Replanning** | Изменение плана по ходу выполнения на основе Observation. | 4 |
| **Reflexion** | Паттерн: Actor → Evaluator → Self-Reflection → Memory → повтор. | 5 |
| **Evaluator** | Компонент Reflexion, оценивающий успех/неудачу. | 5 |
| **Self-Reflection** | LLM пишет «урок» после неудачной попытки. | 5 |
| **Function Calling** | API-метод: LLM возвращает структурированный вызов функции вместо текста. | 6 |
| **JSON Schema** | Схема, описывающая параметры инструмента (типы, обязательность, description). | 6 |
| **Read-only tool** | Инструмент, который не изменяет данные (grep, read, search). | 6 |
| **Write tool** | Инструмент, который изменяет данные (write, edit, delete). | 6 |

## Модуль 3: Память и RAG

| Термин | Определение | Урок |
|--------|-------------|------|
| **Short-term memory** | Контекстное окно (messages[]). Живёт один запрос. | 7 |
| **Working memory** | Данные текущей задачи (plan, scratchpad). Живёт пока выполняется задача. | 7 |
| **Long-term memory** | Знания между сессиями (файлы, БД, wiki). | 7 |
| **RAG** | Retrieval-Augmented Generation: поиск информации во внешнем источнике перед ответом. | 8 |
| **Naive RAG** | Простейший RAG: chunks → embed → search → LLM. | 8 |
| **RAG 2.0** | Production-пайплайн: rewrite → hybrid search → rerank → enrich → generate. | 8 |
| **Hybrid search** | Semantic (embedding) + keyword (BM25) одновременно. | 8 |
| **Reranking** | Пересортировка результатов поиска (LLM или cross-encoder). | 8 |
| **Query rewriting** | Переформулировка запроса пользователя для лучшего поиска. | 8 |
| **GraphRAG** | RAG с графом знаний: сущности и связи между документами. | 8 |
| **LLM Wiki** | Подход Карпати: LLM ведёт wiki из markdown-файлов. | 9 |
| **Raw sources** | Сырые документы (первый слой LLM Wiki). Read-only для LLM. | 9 |
| **Schema** | AGENTS.md — правила структуры wiki (третий слой LLM Wiki). | 9 |
| **Ingest** | Процесс добавления нового источника в wiki. | 9 |
| **Cross-reference** | Связь между wiki-страницами через [[WikiLinks]]. | 9 |
| **Lost-in-the-middle** | Эффект: модель лучше помнит начало и конец контекста, середина теряется. | 1, 7 |

## Модуль 4: Мультиагентные системы

| Термин | Определение | Урок |
|--------|-------------|------|
| **Supervisor** | Топология: менеджер распределяет задачи между агентами. | 10 |
| **Peer-to-peer** | Топология: агенты равны и обмениваются данными напрямую. | 10 |
| **Pipeline** | Топология: каждый агент — шаг конвейера. | 10 |
| **Message Bus** | Асинхронная шина сообщений между агентами (publish/subscribe). | 11 |
| **Handoff** | Передача контекста от одного агента другому. | 11 |
| **Time-out** | Лимит ожидания ответа от агента/инструмента. | 11 |
| **Deadlock** | Циклическое ожидание: Agent1 ждёт Agent2, Agent2 ждёт Agent1. | 12 |
| **Least privilege** | Принцип: каждый агент имеет доступ только к необходимым инструментам. | 12 |
| **Task registry** | Реестр задач: предотвращает дублирование работы агентов. | 12 |

## Модуль 5: Production

| Термин | Определение | Урок |
|--------|-------------|------|
| **Guardrails** | Защитные рельсы: проверка входа, выхода и данных. | 16 |
| **Input guard** | Проверка запроса пользователя на безопасность. | 16 |
| **Output guard** | Проверка действий агента перед выполнением. | 16 |
| **Data guard** | Проверка путей и данных на доступ. | 16 |
| **Prompt injection** | Внедрение инструкций в данные, которые читает агент. | 16 |
| **Block / Confirm / Escalate** | Три стратегии guardrails: блокировать / спросить / передать человеку. | 16 |
| **Observability** | Наблюдаемость: логирование каждого шага агента. | 17 |
| **Trace** | Полная трассировка сессии одного агента (все шаги + cost). | 17 |
| **AgentStep** | Структура одного шага агента: thought, action, args, observation, cost. | 17 |
| **Loop detection** | Детектор зацикливания: если последние N шагов — один инструмент. | 17 |
| **Resilience** | Способность системы продолжать работу после сбоя. | 19 |
| **Exponential backoff** | Стратегия retry: 1s → 2s → 4s → 8s при ошибках API. | 19 |
| **Fallback model** | Запасная модель, если основная недоступна. | 19 |
| **Circuit breaker** | Останавливает агента при too many errors. | 19 |
| **Graceful degradation** | Мягкое падение: если не работает — работает хуже, но работает. | 19 |
| **Cost controller** | Мониторинг бюджета сессии: лимит $ на сессию. | 19 |
| **Eval** | Evaluation: тестирование поведения агента на наборе сценариев. | 20 |
| **Unit test (агент)** | Тест отдельного компонента (guardrails, парсинг, инструмент). | 20 |

## Модуль 6: Prompt Engineering

| Термин | Определение | Урок |
|--------|-------------|------|
| **RCTFCE** | Role + Context + Task + Format + Constraints + Examples (анатомия промпта). | 21 |
| **Императивность** | Правило: «делай X», а не «пожалуйста, сделай X». | 21 |
| **Позитивные инструкции** | «делай X вместо Y» работает лучше, чем «не делай Y». | 21 |
| **Zero-shot** | Промпт без примеров. | 22 |
| **Few-shot** | Промпт с 2-5 примерами. | 22 |
| **Chain-of-Thought (CoT)** | «Давай подумаем пошагово» — улучшает рассуждение модели. | 22 |
| **Structured CoT** | Thought → Action → Observation (ReAct-формат). | 22 |
| **JSON mode** | `response_format={"type": "json_object"}` — модель возвращает JSON. | 23 |
| **Structured Output** | Любой способ заставить LLM вернуть структурированные данные. | 23 |
| **Grammar-based** | GBNF грамматика — ограничение вывода (для локальных моделей). | 23 |

## Общие термины

| Термин | Определение |
|--------|-------------|
| **HITL** | Human-in-the-loop: человек в цикле принятия решений. |
| **Fine-tuning** | Донастройка LLM на своих данных (не входит в курс). |
