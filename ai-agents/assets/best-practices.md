# Best Practices для AI-агентов — Май 2026

Сводка правил, проверенных на практике при проектировании, разработке и эксплуатации AI-агентов.

---

## 1. Выбор паттерна

| Если задача... | Используй | Почему |
|---------------|-----------|--------|
| 1-5 шагов, exploratory | **ReAct** | Дешевле, быстрее, гибче |
| 10+ шагов, важен порядок | **Plan-and-Solve** | План не даёт сбиться |
| Ошибка дорого стоит | **Reflexion** | MAX_TRIALS=3 спасает бюджет |
| Нужно разделить обязанности | **Supervisor** | Меньше конфликтов |
| Важна скорость | **Pipeline** | Каждый агент — шаг конвейера |

## 2. Размер system prompt

| Размер | Когда |
|--------|-------|
| < 500 токенов | Идеально: роль + 3 правила |
| 500-2000 | Нормально: роль + правила + формат |
| 2000-4000 | Плохо: модель теряет фокус. Разбей на части |
| > 4000 | Критично: вынеси в skills, оставь только ядро |

## 3. Инструменты

- **Один инструмент — одно действие** — `search_files()`, а не `do_stuff()`
- **Read-only инструменты — без подтверждения** — grep, read, search
- **Write-инструменты — с confirm** — write, edit, delete
- **Dangerous — block** — deploy, sudo, rm
- **Description обязателен** — модель выбирает инструмент по description
- **Не больше 10-15 инструментов на агента**

## 4. Память

- **Short-term** — только последние 20-30 сообщений, остальное в working
- **Working** — JSON-файл на диске, план + текущий шаг
- **Long-term** — markdown-файлы (LLM Wiki по Карпати)
- **Сжатие контекста** — при 70% заполнения (WARN), при 85% — COMPRESS

## 5. Guardrails

- **Input guard** — проверка запроса: prompt injection, опасные темы
- **Output guard** — проверка действия: белый список команд
- **Data guard** — проверка пути: только разрешённые директории
- **Стратегия:** `allow` для read, `confirm` для write, `block` для dangerous, `escalate` для подозрительного

## 6. Resilience

- **Retry:** 3 попытки, exponential backoff (1s → 2s → 4s)
- **Fallback:** main model → cheap model → error
- **Circuit breaker:** 5 ошибок подряд → стоп
- **Budget:** $0.05-0.10 на сессию
- **Timeout:** 30s на вызов LLM, 10s на инструмент

## 7. Prompt Engineering

- **Role задаёт стандарт** — «senior» ≠ «junior»
- **Императив** — «сделай X» > «пожалуйста, сделай X»
- **Формат** — всегда указывай (JSON / markdown / код)
- **Примеры** — 2-3 для сложных форматов
- **Одна задача** — один промпт

## 8. Skills

- **Один skill в момент времени**
- **Чеклист важнее прозы** — модель следует пунктам
- **YAML frontmatter обязателен** — name, description, version
- **depends_on** — для связывания skills
- **Версионирование** — semver (1.0.0 → 1.1.0 → 2.0.0)

## 9. Оценка и тестирование

- **Unit-тесты** — компоненты (guardrails, парсинг)
- **Integration** — связки (агент + инструменты)
- **Evals** — поведение на наборе сценариев
- **CI** — прогон evals перед каждым деплоем
- **Метрики:** pass rate, cost, steps, duration

## 10. Чего НЕ делать (антипаттерны)

- ❌ Один агент на всё — разделяй обязанности
- ❌ Без guardrails — «LLM сама разберётся» ≠ работает
- ❌ Бесконечная рефлексия — MAX_TRIALS=3
- ❌ Вся история в short-term — используй working memory
- ❌ Два активных skill одновременно — конфликт ролей
- ❌ Сложная JSON Schema (20 полей) — 3-5 полей на уровень
- ❌ Проверять ответ LLM дословно — проверяй паттерн
