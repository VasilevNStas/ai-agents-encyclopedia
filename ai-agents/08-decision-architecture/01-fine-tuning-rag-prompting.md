# Урок 28: Fine-tuning vs RAG vs Prompting — decision matrix

> [!quote] Ключевая идея
> Три подхода к адаптации LLM под задачу — это не конкуренты, а инструменты с разными характеристиками. Архитектор выбирает не «лучший», а **соответствующий** ограничениям: latency, cost, quality, control.

---

## Три оси выбора

```
Prompt Engineering
    └── быстрее всего, хрупче всего
    └── меняешь поведение текстом

RAG (Retrieval-Augmented Generation)
    └── добавляешь знания внешними данными
    └── не меняешь поведение модели

Fine-tuning
    └── меняешь поведение модели весами
    └── дорого, необратимо
```

Каждый подход меняет **разные** аспекты системы:

| Аспект | Prompt Engineering | RAG | Fine-tuning |
|--------|-------------------|-----|-------------|
| Знания | Контекст | Внешний источник | Веса модели |
| Поведение | Инструкцией | Не меняет | Навсегда |
| Скорость итерации | Секунды | Часы | Дни-недели |
| Стоимость | ~0 | $ (датасет + инфра) | $$$ (GPU) |
| Риск | Хрупкость | Зависимость от поиска | Catastrophic forgetting |
| Контроль | Полный | Ограничен качеством данных | Полный (но дорогой) |

---

## Prompt Engineering — когда хватает текста

Prompt engineering — самый быстрый способ изменить поведение модели. Ничего не нужно тренировать или индексировать.

### Когда использовать

```python
def choose_prompt_engineering(task: str) -> bool:
    """Prompt engineering достаточен, если:"""
    conditions = [
        "нужен новый формат вывода" in task,
        "нужно изменить стиль" in task,
        "задача в рамках знаний модели" in task,
        "нет сверхспецифичной терминологии" in task,
        "быстрое прототипирование" in task,
    ]
    return any(conditions)
```

**Примеры:**
- Форматирование вывода (JSON, markdown, таблицы)
- Смена тона (формальный, дружелюбный, технический)
- Добавление чеклистов и правил
- few-shot с примерами из задачи

**Ограничения:**
- Контекстное окно — не бесконечно
- Сложные инструкции модель может игнорировать
- Нет «памяти» между сессиями
- Галлюцинации на редких темах

---

## RAG — когда знания снаружи

RAG добавляет модели доступ к внешним данным без изменения весов. Модель получает контекст при каждом запросе.

### Когда использовать

```python
def choose_rag(task: str) -> bool:
    """RAG необходим, если:"""
    conditions = [
        "нужны актуальные данные" in task,
        "есть собственная база знаний" in task,
        "частые обновления информации" in task,
        "редкие или специфичные термины" in task,
        "гарантия фактологической точности" in task,
    ]
    return any(conditions)
```

**Примеры:**
- Документация продукта (обновляется каждый релиз)
- Юридические/медицинские справочники
- Кодовая база проекта
- Поддержка клиентов с базой знаний

**Ограничения:**
- Зависит от качества поиска (chunking, embedding, reranking)
- Добавляет latency (search + rerank)
- Контекст может быть зашумлён
- Не меняет поведение модели — только факты

---

## Fine-tuning — когда нужно изменить саму модель

Fine-tuning меняет веса модели, обучая её на ваших данных. Это самый мощный, но и самый дорогой инструмент.

### Когда использовать

```python
def choose_finetuning(task: str) -> bool:
    """Fine-tuning оправдан, если:"""
    conditions = [
        "специфичный формат или язык" in task,
        "модель систематически ошибается" in task,
        "нужна скорость без RAG-пайплайна" in task,
        "стабильное поведение без промптов" in task,
        "конфиденциальные данные нельзя передавать API" in task,
    ]
    return any(conditions)
```

**Примеры:**
- Специфичный корпоративный жаргон
- Генерация кода на внутреннем DSL
- Извлечение данных в кастомный формат
- Запуск on-premise без доступа к API

**Ограничения:**
- Дорого (GPU, датасет, инженер)
- Catastrophic forgetting — модель может разучиться делать то, что умела
- Сложно итерировать (дни на обучение)
- Нужен качественный датасет (сотни-тысячи примеров)

---

## Decision Tree: что выбрать

```
Задача — добавить новые знания?
  ├── Да → RAG (данные обновляются) или Fine-tuning (статика)
  └── Нет
       │
       ▼
Задача — изменить поведение/формат?
  ├── Да → Prompt engineering (если влезает в контекст)
  │         └── Не влезает → Fine-tuning
  └── Нет
       │
       ▼
Нужна гарантия точности?
  ├── Да → RAG + валидация
  └── Нет → Prompt engineering (самый быстрый)
```

## Комбинированные стратегии

В production чаще всего используется комбинация:

```
┌─────────────────────────────────┐
│          System Prompt          │ ← конституция, правила
├─────────────────────────────────┤
│  Prompt Engineering (few-shot)  │ ← примеры формата
├─────────────────────────────────┤
│       RAG (search + rerank)     │ ← фактические знания
├─────────────────────────────────┤
│    Fine-tuning (опционально)    │ ← специализация поведения
└─────────────────────────────────┘
```

### Стратегия «Prompt + RAG» (самая частая)

```python
def prompt_plus_rag(query: str, docs: list[str]) -> str:
    context = rag_search(query, docs)
    prompt = f"""
    Ты — эксперт. Отвечай на основе контекста.
    Если в контексте нет ответа — скажи, что не знаешь.

    Контекст: {context}

    Вопрос: {query}
    """
    return llm.generate(prompt)
```

**Когда:** 80% production-агентов. Быстро, гибко, контролируемо.

### Стратегия «Fine-tune + RAG» (для продакшена)

```python
def finetune_plus_rag(query: str, docs: list[str]) -> str:
    # Модель уже fine-tuned на формат ответа
    context = rag_search(query, docs)
    # Промпт минимальный — поведение в весах
    prompt = f"Контекст: {context}\nВопрос: {query}\nОтвет:"
    return finetuned_model.generate(prompt)
```

**Когда:** нужна скорость, стабильность формата, и данные конфиденциальны.

### Стратегия «Все три» (максимум контроля)

```
1. Fine-tuning задаёт базовое поведение (формат, стиль)
2. System prompt добавляет правила (безопасность, контекст)
3. RAG подставляет актуальные факты
4. Prompt engineering на лету адаптирует под задачу
```

## Когда ни один подход не нужен

| Сценарий | Что делать вместо |
|----------|------------------|
| Нужен точный ответ из БД | SQL / API / grep |
| Нужна математика | Калькулятор / WolframAlpha |
| Нужен поиск по коду | IDE tools / grep / GRACE |
| Нужно выполнить действие | Вызвать инструмент / функцию |
| Творческая задача без фактов | LLM as-is, без RAG/fine-tune |

## Пример: реальный кейс

**Задача:** агент поддержки клиентов для SaaS-продукта.

```
Требования:
- Отвечать на вопросы по документации (обновляется еженедельно)
- Соблюдать tone of voice компании
- Не разглашать внутреннюю информацию
- Быстро (latency < 2s)

Решение:
1. Prompt engineering → tone of voice, политика безопасности
2. RAG → документация продукта (еженедельное обновление)
3. Fine-tuning → не нужен (достаточно промпта + RAG)

Итого: 2 подхода, 0 fine-tuning, production за неделю.
```

---

## Резюме

```
Prompt Engineering: быстро, дёшево, хрупко
RAG:               факты извне, гибко, зависит от поиска
Fine-tuning:       меняет модель, мощно, дорого

Правило архитектора:
  Начни с промпта.
  Если не хватает знаний — добавь RAG.
  Если не хватает поведения — fine-tuning.
  Комбинируй, когда нужно.
  Не делай ничего из этого, если можно решить инструментом.
```
