# Порог 1% (One Percent Rule)

**Время чтения:** 6 мин

## Суть

Если есть хотя бы 1% вероятности, что skill подходит под задачу — агент ОБЯЗАН его загрузить. Это правило — защита от false negative: ситуаций, когда агент решает "не проверять" skill, который мог бы быть полезен.

## Основной материал

### Происхождение правила

Почему именно 1%, а не 0% или 100%?

- **0%** означало бы, что агент никогда не загружает skill, если не уверен на 100%. На практике агенты постоянно сомневаются — и пропускают полезные skills.
- **100%** означало бы, что агент загружает каждый skill подряд. Это неэффективно: множество false positive срабатываний съедает контекст и время.
- **1%** — компромисс: достаточно низкий порог, чтобы не пропустить релевантный skill, но достаточно высокий, чтобы не загружать всё подряд.

Правило родилось из эмпирического наблюдения: когда у агента нет жёсткого порога, он систематически **недо-использует** skills (under-utilization). Слово "1%" — метафора, а не математика. Не нужно вычислять точную вероятность.

### Проблема, которую решает правило

Без 1% агент думает:

> "Hmm, skill might fit but I'm not sure. Let me skip it and just do it manually."

Это **рационализация**. Агент находит причину не загружать skill, потому что:
- Не хочет тратить время на загрузку
- Считает, что "помнит" содержание skill
- Думает, что задача "слишком простая" для skill
- Уверен, что справится сам

Правило 1% блокирует эту рационализацию: если есть хоть тень сомнения — загружай.

### Как это работает на практике

| Мысль агента | Решение |
|-------------|---------|
| "Этот skill для React, а мы на Vue — точно не подходит" | Не загружать |
| "Этот skill для багов, а у нас задача — написать фичу" | Не загружать |
| "Этот skill для TDD, а у нас написание тестов... ну, вроде подходит" | Загрузить (1% есть) |
| "Пользователь говорит про код-ревью, а skill называется requesting-code-review..." | Загрузить (даже не уверен) |

### Описание description — ключ к триггерингу

Description — единственное, на что опирается агент на этапе оценки. От него зависит, сработает 1% или нет.

- **Узкое описание** — "Use only when encountering Python import errors" — редко срабатывает, но метко.
- **Широкое описание** — "Use when encountering any bug, test failure, or unexpected behavior" — срабатывает часто, включая случаи, где skill не совсем уместен.

### Как измеряют качество триггеринга

Официальная метрика Anthropic: skill должен триггериться на **90% релевантных запросов**. Для тестирования используется набор eval-запросов:

```json
[
  { "query": "напиши тесты для модуля X", "should_trigger": true },
  { "query": "как переименовать файл", "should_trigger": false }
]
```

Каждый запрос прогоняется 3 раза, вычисляется trigger rate. Подробнее — в [Evaluating skill output quality](https://agentskills.io/skill-creation/evaluating-skills).

### Когда 1% не срабатывает

Правило — это инструкция агенту, а не алгоритм. Модель может:
- Неверно интерпретировать описание skill
- "Забыть" проверить skill (особенно в длинных сессиях)
- Ошибиться в оценке релевантности

Единственная защита — хорошее описание skills и тестирование через eval-запросы.

### Влияние сложности задачи

Важный нюанс: агенты обычно применяют skills только к задачам, требующим знаний или возможностей сверх базовых. Простой одношаговый запрос ("прочитай этот PDF") может не триггернуть skill, даже если description совпадает идеально — потому что агент справляется базовыми инструментами.

## Кейс

Разработчик пишет: "добавь новую команду в CLI". Агент проверяет список skills. Среди них есть `writing-skills` с description "Use when creating new skills, editing existing skills, or verifying skills work before deployment". Агент думает: "Задача не про создание skills, а про CLI — но описание упоминает 'creating new', и вообще 1% есть". Загружает — и внутри находит шаблон создания файлов, который пригодился для структуры CLI. Без 1% агент бы пропустил.

## Упражнение

Посмотри на описание любого установленного skill. Насколько оно широкое? Может ли оно сработать для задачи, под которую skill не предназначен? Если да — предложи, как сузить описание.

## Ключевые выводы

- Правило 1% — защита от false negative (пропущенных skills)
- Порог метафорический: "не однозначно нет" = 1% = загружай
- Правило не гарантирует загрузку — model miss возможна
- Качество триггеринга измеряется через eval-запросы (цель — 90%)
- Простые задачи могут не триггерить skills даже при точном совпадении description
