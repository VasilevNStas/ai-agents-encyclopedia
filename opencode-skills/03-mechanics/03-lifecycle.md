# Жизненный цикл skill в сессии

**Время чтения:** 7 мин

## Суть

Каждый skill, загруженный агентом, проходит три последовательных этапа (progressive disclosure): от метаданных до полного выполнения. Понимание этого цикла помогает правильно проектировать skills и диагностировать проблемы.

## Основной материал

### Три этапа жизненного цикла

```
Discovery (метаданные) → Activation (SKILL.md) → Execution (инструкции)
```

#### 1. Discovery (Обнаружение)

Происходит при старте сессии. Агент сканирует все доступные директории skills:

- `node_modules/` — npm-пакеты с флагом superpowers
- `.opencode/skills/` — локальные проектные skills
- `~/.claude/skills/` — глобальные для Claude Code
- `.agents/skills/` — универсальный путь

На этом этапе читаются **только name и description** из YAML frontmatter. Полный SKILL.md **ещё не загружен**. Результаты сканирования кэшируются.

#### 2. Activation (Активация)

Когда пользователь даёт задачу, агент:

1. Сопоставляет description каждого известного skill с задачей (семантическое сходство + порог 1%)
2. Для подходящих skills вызывает Skill Tool: `skill("name")`
3. Система находит директорию, читает SKILL.md и возвращает содержимое
4. Агент добавляет инструкции в контекст

Множественные skills: если подходят несколько, все загружаются. Порядок — по релевантности (от наиболее совпавшего).

#### 3. Execution (Выполнение)

Агент следует инструкциям из SKILL.md:

- Выполняет описанные шаги
- При необходимости подгружает файлы из `scripts/`, `references/`, `assets/`
- По завершении задачи skill **покидает активный контекст**

Каждая новая задача запускает полный цикл заново. Skill НЕ остаётся в контексте "на всякий случай".

### Dot-граф жизненного цикла

```
digraph lifecycle {
    "Старт сессии" -> "Discovery" [label="сканирование директорий"];
    "Discovery" -> "Зарегистрировано" [label="name + description"];
    "Пользователь" -> "Activation" [label="задача"];
    "Зарегистрировано" -> "Activation" [label="match >= 1%"];
    "Activation" -> "Execution" [label="SKILL.md загружен"];
    "Execution" -> "Завершение" [label="задача выполнена"];
    "Завершение" -> "Discovery" [label="новая задача"];

    "Зарегистрировано" -> "Пропуск" [label="match < 1%"];
    "Activation" -> "Ошибка" [label="skill не найден"];
}
```

### Когда skill НЕ загружается

- **Match < 1%** — описание не совпало с задачей
- **Skill не найден** — директория удалена или переименована
- **SUBAGENT-STOP** — дочерний агент пропустил загрузку
- **Слишком простая задача** — агент справляется без skill

Это нормальные, рабочие сценарии. Не каждый запрос требует skill.

### Множественные skills

Если подходят несколько skills, агент загружает все в порядке релевантности:

```
// Задача: "напиши тесты для новой фичи"
1. test-driven-development  (match: 95%)
2. brainstorming            (match: 40%)
3. requesting-code-review   (match: 15%)
```

Порядок загрузки важен: первый skill определяет подход, остальные накладываются поверх.

### Ограничения

- Skill не может загрузить другой skill напрямую — только агент решает
- SKILL.md рекомендуется держать до 500 строк / 5000 токенов
- Оптимальное количество одновременно загруженных: 2-4, максимум 20-50
- Рекурсивная загрузка skills невозможна

## Кейс

Агент получает запрос: "пофикси баг в payment processing". Discovery: на этапе старта сессии уже известен `systematic-debugging`. Activation: description совпадает ("Use when encountering any bug") → загрузка SKILL.md. Execution: выполнение чеклиста — сбор контекста, воспроизведение бага, root cause, фикс. Завершение: skill выгружен. Следующий запрос — без влияния предыдущего skill.

## Ключевые выводы

- Жизненный цикл: Discovery (метаданные) → Activation (SKILL.md) → Execution (инструкции)
- При старте сессии загружаются только метаданные (progressive disclosure)
- Каждая новая задача запускает полный цикл заново
- Если несколько skills подходят — все загружаются в порядке релевантности
- Skill выгружается после завершения задачи
