# Кэширование и оптимизация загрузки

**Время чтения:** 6 мин

## Суть

Skills используют lazy loading и кэширование метаданных для экономии контекста. Понимание этих механизмов помогает проектировать эффективные skills и избегать ошибок при обновлении пакетов.

## Основной материал

### Lazy loading

Skills не загружаются до первого совпадения с задачей. Это базовый механизм экономии контекста:

```
При старте сессии:
  → Агент сканирует директории
  → Регистрирует name + description (~100 токенов на skill)
  → SKILL.md НЕ читается

При запросе пользователя:
  → Агент сравнивает задачу с description каждого skill
  → Если match >= 1% — загружает полный SKILL.md
  → Если нет — skill остаётся незагруженным
```

**Эффект:** 50 установленных skills = ~5000 токенов метаданных, а не 25000+ токенов полных инструкций.

### Кэширование метаданных

Результаты сканирования директорий кэшируются. Повторное сканирование происходит только при:
- Установке нового пакета (`npm install`)
- Явном перезапуске сессии
- Изменении конфигурации

Это значит, что если ты добавил новый skill в `.opencode/skills/` во время сессии, агент может его не увидеть до перезапуска.

**Решение:** перезапусти сессию после добавления нового skill.

### Что кэшируется, а что нет

| Данные | Кэшируются | Когда обновляются |
|--------|-----------|------------------|
| name + description | Да | При перезапуске сессии |
| Список доступных skills | Да | При перезапуске сессии |
| Полный SKILL.md | Нет | Читается при каждом вызове |
| Файлы из scripts/ | Нет | Читаются при необходимости |

Полный SKILL.md не кэшируется — при каждом вызове `skill("name")` система читает файл заново. Это гарантирует, что изменения в SKILL.md применяются сразу (после перезапуска сессии).

### Когда кэширование может навредить

**Проблема:** skill обновился (новая версия пакета), но агент использует старые name+description из кэша.

**Сценарий:**
1. Пользователь установил пакет v1.0
2. Агент закэшировал метаданные
3. Пользователь обновил до v2.0 (другой description)
4. Агент всё ещё видит старый description из кэша
5. Skill не триггерится на новые типы задач

**Решение:** перезапусти сессию после обновления пакетов.

### Оптимизация загрузки

**1. Группировка часто используемых skills**

Если два skills всегда загружаются вместе, объедини их в один:
- `commit-formatter` + `commit-message-validator` → `commit-assistant`

**2. Разделение редких и частых skills**

Часто используемые skills должны быть компактными (< 150 слов). Редкие могут быть больше — они загружаются редко.

**3. Использование SUBAGENT-STOP**

Предотвращает двойную загрузку skills в дочерних агентах. Если skill уже загружен в родителе, subagent не будет загружать его снова.

### Перспективы

**Кэширование SKILL.md на уровне сессии.** Если один skill вызывает другой несколько раз, полный SKILL.md может кэшироваться в рамках сессии. Это особенно актуально для skill chaining.

**Автоматическая инвалидация кэша.** При обновлении пакета агент может автоматически сбрасывать кэш метаданных для этого пакета.

**Разделяемое кэширование между сессиями.** Метаданные skills могут кэшироваться на диске, чтобы не сканировать node_modules при каждом старте.

## Кейс / пример

Установлено 20 пакетов, каждый с 3-5 skills. Итого 80 зарегистрированных skills. В любой момент времени загружено 0-2 (те, чей description совпал с задачей). Остальные 78 занимают ~7800 токенов — только name и description в метаданных.

Если бы все 80 skills загружали полные SKILL.md (в среднем 500 токенов) — это было бы 40K токенов (40% окна). Lazy loading экономит ~90% контекста.

## Ключевые выводы

- Lazy loading: skills не загружаются до match'а — экономия ~90% контекста
- Метаданные кэшируются при старте сессии
- Полный SKILL.md читается заново при каждом вызове
- Перезапускай сессию после добавления/обновления skills
- Группируй часто используемые skills, разделяй редкие и частые
