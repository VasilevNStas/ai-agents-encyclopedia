# Модуль 2: Анатомия промта

> [!quote] Ключевая идея
> Промт — это код. Он состоит из 8 элементов с разной критичностью.
> Задача инженера — знать каждый элемент и понимать, когда он обязателен,
> а когда опционален.

---

## 1. Что такое промт

**Промт** — это инструкция для LLM, которая задаёт поведение, контекст и формат ответа.

### Ментальная модель

```
LLM — это исполнитель, который:
- Идеально следует инструкциям (но буквально)
- Ничего не помнит между вызовами (если нет инструментов)
- Не знает, чего вы НЕ хотите (надо явно сказать)
- Предсказывает следующий токен, а не «думает»
```

### Две части промта

| Часть | Назначение | Кто задаёт |
|-------|------------|------------|
| **System prompt** | Роль, контекст, правила, формат, ограничения | Разработчик системы |
| **User prompt** | Конкретная задача, данные, запрос | Пользователь / система |

**Правило:** System задаёт сцену. User — действие. Не смешивай.

## 2. Восемь элементов промта

```
┌─────────────────────────────────────────────────────┐
│                  СИСТЕМНЫЙ ПРОМТ                    │
│[Персона] [Контекст] [Правила] [Формат] [Guardrails] │
├─────────────────────────────────────────────────────┤
│                 ПОЛЬЗОВАТЕЛЬСКИЙ ПРОМТ              │
│  [Инструкция] [Данные] [Примеры] [Вопрос]           │
└─────────────────────────────────────────────────────┘
```

### A. Персона (Role) — ★★★ обязательно для production

Кем LLM должна себя считать.

```
Ты — senior SQL-разработчик с 10-летним опытом.
```

**Почему:** Персона задаёт тон, глубину, стиль. Без персоны LLM выбирает «нейтрального помощника» — часто слишком общего и многословного.

Когда можно пропустить: задачи без ролевого контекста (простой перевод, форматирование).

### B. Контекст (Context) — ★★★ обязательно всегда

Что нужно знать LLM для выполнения задачи.

```
Ты работаешь с PostgreSQL 16, база данных интернет-магазина.
Схема: users(id, name, email), orders(id, user_id, total, created_at)
```

**Правило:** Давай релевантный контекст. Не перегружай — отсекай лишнее. Каждый токен стоит денег.

### C. Инструкция (Instruction) — ★★★ обязательно всегда

Что именно сделать. Один глагол на одну инструкцию.

```
Напиши SQL-запрос, который покажет топ-10 пользователей по сумме заказов за последний месяц.
```

**Правило:** Одна инструкция — одно действие. Если задач несколько — нумеруй:

```
1. Напиши SQL-запрос для топ-10 пользователей
2. Объясни, почему используется именно этот индекс
3. Предложи альтернативу с оконной функцией
```

### D. Данные (Input Data) — ★★☆ важно

Входные данные для обработки. Шаблонизируй через {{placeholders}}.

```xml
<data>
  <user_name>Иван</user_name>
  <user_email>ivan@example.com</user_email>
</data>
```

**Best practice:** Отделяй данные от инструкции разметкой (XML/JSON/markdown). Это защищает от prompt injection и улучшает парсинг.

### E. Формат вывода (Output Format) — ★★★ обязательно для production

Как должен выглядеть ответ.

```
Ответ верни в JSON:
{
  "query": "string",
  "explanation": "string",
  "index_used": "string"
}
```

**Best practice:** Для JSON — давай схему. Для текста — давай шаблон. Без формата LLM выберет его сама, и он будет непредсказуем.

### F. Примеры (Few-Shot / Examples) — ★★☆ важно

Покажи, как должен выглядеть правильный ответ.

**Best practice:** 1-3 примера достаточно. Больше — только если задача сложная. Примеры должны быть разнообразными.

### G. Ограничения / Guardrails — ★★☆ важно для production

Что НЕЛЬЗЯ делать.

```
- НЕ используй DELETE без WHERE
- НЕ предполагай схему — используй ТОЛЬКО предоставленные таблицы
- ЕСЛИ не уверен — напиши "-- Требуется уточнение"
```

**Принцип:** Формулируй позитивно, где возможно. «Используй только предоставленные таблицы» лучше, чем «Не придумывай таблицы».

### H. Chain-of-Thought триггер — ★☆☆ опционально

Заставь LLM рассуждать перед ответом.

```
Прежде чем писать финальный ответ, распиши свои рассуждения шаг за шагом.
```

**Правило:** CoT нужен для сложных (логических, многошаговых) задач. Для простых — только добавляет latency и токены.

## 3. Матрица критичности

| Элемент | MVP промта | Production | Когда пропустить |
|---------|------------|------------|------------------|
| Персона | Опционально | Обязательно | Задачи без ролевого контекста |
| Контекст | **Обязательно** | Обязательно | Никогда |
| Инструкция | **Обязательно** | Обязательно | Никогда |
| Данные | Зависит от задачи | Обязательно | Если данных нет |
| Формат вывода | Опционально | Обязательно | Чат / творчество |
| Примеры | Опционально | Часто нужно | Простые / очевидные задачи |
| Guardrails | Опционально | Обязательно | Одноразовые эксперименты |
| CoT | Опционально | Опционально | Простые задачи |

### MVP промт (минимально жизнеспособный)

**MVP промт** (от англ. _Minimum Viable Product Prompt_) — это максимально точный, структурированный запрос к нейросети, цель которого — получить за один раз (или пару итераций) готовый, рабочий результат: прототип кода, описание концепции, план маркетинга или контент для проверки бизнес-гипотезы

Простыми словами, это **«техническое задание на минималках» для ИИ**, чтобы быстро понять, будет ли идея работать, не тратя недели на разработку

Структура хорошего MVP промта:
Чтобы ИИ выдал работающий MVP, промт должен содержать следующие элементы:

1. **Роль:** «Ты — опытный Fullstack-разработчик...».
2. **Задача:** «Создай одностраничное приложение на React...».
3. **Контекст и цель:** «...которое позволяет пользователю записаться на стрижку...».
4. **Минимальный функционал (MVP):** «...нужна только форма ввода имени, телефона и выбор времени. База данных не нужна, достаточно вывода в консоль».
5. **Ограничения/Стек:** «Используй Tailwind CSS для стилей, сделай адаптивно»


Чем MVP промт отличается от обычного?

|Характеристика [[1](https://cloud.ru/docs/ai-agents/ug/topics/concepts__write_prompts), [2](https://www.reddit.com/r/ChatGPT/comments/1mzh2zl/feedback_wanted_refining_a_prompt_for_fast_mvp/?tl=ru), [3](https://code9.studio/uslugi/mvp-s-ai)]|Обычный промт|MVP промт|
|---|---|---|
|**Цель**|Получить информацию/идею|Получить готовый результат (код, текст)|
|**Детализация**|Общая|Высокая (роль, контекст, ограничения)|
|**Результат**|«На подумать»|«В продакшн» (можно тестировать)|

```
[Контекст] + [Инструкция] + [Данные]
```

Этого достаточно, чтобы LLM сделала хоть что-то.

Примеры MVP промтов

- **Для IT-продукта:** «Действуй как Python-разработчик. Напиши код для Telegram-бота, который принимает email от пользователя и сохраняет его в Google Таблицу. Используй библиотеку aiogram. Напиши самый простой код для проверки».
- **Для контента:** «Ты маркетолог. Напиши 5 вариантов коротких рекламных заголовков для MVP-сервиса по доставке здорового питания для офисных работников. Цель: кликбейт, высокий CTR»

Ключевые принципы

- **Убирайте лишнее:** В MVP промте нет места «красивостям» и сложной логике. Только то, что нужно для проверки спроса.
- **Быстрый результат:** Продукт, созданный по такому промту, должен быть готов к тестированию в течение нескольких часов.
- **Итеративность:** Часто MVP промт — это начало диалога. Получив первый черновик от ИИ, вы уточняете его в следующем запросе

### Production-промт

```
[Персона] + [Контекст] + [Инструкция] + [Данные] + [Формат] + [Guardrails] + [Примеры]
```

Этот промт даёт предсказуемый, контролируемый результат.

## 4. Best Practices

### Структурированные промты

Используй разметку для отделения секций.

```
Ты — эксперт по {{domain}}.

## Контекст
{{context}}

## Задача
{{task}}

## Данные
{{data}}

## Формат ответа
{{format}}

## Ограничения
{{constraints}}
```

### Explicit beats implicit

| Вместо | Лучше |
|--------|-------|
| «Будь краток» | «Ответ не более 3 предложений» |
| «Используй правильный формат» | «Ответь в JSON: {"key": "value"}» |
| «Будь профессионален» | «Используй деловой тон, без сленга и эмодзи» |

### Temperature-first tuning

1. Сначала настрой промт при temp=0.0 (детерминированный режим)
2. Потом подними temperature до нужного уровня

## 5. Антипаттерны

| Антипаттерн | Проблема | Решение |
|-------------|----------|---------|
| «Будь умным» | Размытая инструкция | Конкретная задача |
| Всё в system prompt | Смешение правил и данных | Раздели system/user |
| Слишком длинные примеры | Перегрузка контекста | 1-3 коротких примера |
| Противоречивые инструкции | LLM следует последней | Проверь логику |
| Неявные ожидания | «Ну ты понял» — не понял | Явный формат |
| Игнор ошибок LLM | «Просто попроси лучше» | Добавь guardrails |

## Практика: От MVP к Production

> [!tip] Задание
> Возьми MVP-промт и последовательно добавь каждый элемент, пока не получишь production-промт.

### Шаг 1: MVP

```
Напиши письмо клиенту о задержке доставки.
Клиент: Иван Петров
Заказ: №12345
Новая дата: 15 мая
```

### Шаг 2: Добавь контекст и инструкцию (уже есть — ok)

### Шаг 3: Добавь персону

```
Ты — вежливый менеджер поддержки интернет-магазина.
```

### Шаг 4: Добавь формат вывода

```
Ответ в формате:
Тема: ...
Уважаемый {имя}, ...
...
С уважением, команда поддержки
```

### Шаг 5: Добавь guardrails

```
- НЕ обещай компенсацию без согласования
- ЕСЛИ клиент спрашивает про возврат — сообщи, что вопрос передан в отдел возвратов
```

### Шаг 6: Добавь пример

```
Вход: Клиент: Анна Смирнова, Заказ: №67890, Новая дата: 20 мая
Ответ:
Тема: Задержка доставки заказа №67890
Уважаемая Анна,
Приносим извинения за задержку. Ваш заказ будет доставлен 20 мая.
С уважением, команда поддержки
```

**Итог:** Из 3 строк получили структурированный production-промт из 7 элементов.
