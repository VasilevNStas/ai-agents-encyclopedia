# Модуль 8b: Fine-tuning Pipeline — когда промпта не достаточно

> [!quote] Ключевая идея
> Fine-tuning — это не "лучшая версия промптинга". Это **другой инструмент**. Промптинг меняет поведение модели через контекст. Fine-tuning меняет веса модели через данные. Понимание разницы — выбор правильного подхода под задачу.

---

## 1. Что такое fine-tuning (ментальная модель)

Базовая модель обучена на триллионах токенов из интернета. Fine-tuning — это дообучение на специализированном датасете, чтобы модель лучше выполняла конкретную задачу.

```
Базовая модель:
  Обучена: интернет (триллионы токенов)
  Умеет: общий язык, факты, рассуждения
  Не умеет: специфический формат, стиль, домен

После fine-tuning:
  Обучена: специализированные данные (тысячи примеров)
  Умеет: специфический формат + общие способности сохранены
```

Важно: fine-tuning **не добавляет новые знания**. Он меняет **формат и стиль** ответа. Новые знания даёт только RAG.

## 2. LoRA / QLoRA — как fine-tuning работает на практике

### Полный fine-tuning (Full FT)

Обновляются все веса модели. Дорого, медленно, нужна копия модели для каждой задачи.

```
Full FT:
  Параметры: 70B (все)
  Память: ~280 GB GPU
  Время: дни
  Результат: отдельная копия модели под задачу
```

### LoRA (Low-Rank Adaptation)

Заморозить все веса, добавить маленькие адаптеры:

```
LoRA:
  Параметры: 0.1-1% от оригинала
  Память: ~16 GB GPU (для 7B модели)
  Время: часы
  Результат: адаптер (5-50 MB) + базовая модель
```

```python
# Концептуально: LoRA добавляет маленькие матрицы к слоям attention
# Оригинальные веса заморожены
# Обучаются только LoRA-адаптеры

# До:
output = W @ input      # W = 4096x4096 (16M параметров)

# После LoRA:
output = W @ input + (B @ A) @ input   # A=4096x8, B=8x4096 (65K параметров)
# W — заморожен (не обучается)
# A, B — обучаются (0.4% от W)
```

### QLoRA — Quantized LoRA

LoRA + квантизация базовой модели до 4-8 бит:

```
QLoRA:
  Базовая модель: 4-bit quantized
  Адаптер: 16-bit (точный)
  Память: ~6 GB GPU (для 7B модели)
  Время: часы
  Результат: адаптер (5-50 MB)
```

**Правило выбора:**

| Сценарий | Подход | VRAM | Скорость |
|----------|--------|------|----------|
| Эксперимент, прототип | QLoRA | 6-12 GB | Средне |
| Production, одна задача | LoRA | 12-24 GB | Быстро |
| Несколько задач | LoRA + adapter switching | 12 GB | Быстро |
| Полный контроль | Full FT | 80+ GB | Медленно |

## 3. RLHF vs DPO — две философии

### RLHF (Reinforcement Learning from Human Feedback)

Классический подход (InstructGPT, 2022):

```
1. SFT (Supervised Fine-Tuning):
   Датасет: демонстрации (человек показывает, как отвечать)

2. Reward Model:
   Датасет: сравнения (какой ответ лучше?)
   → модель, которая оценивает качество ответа

3. RL (PPO):
   Промпт → LLM → ответ → Reward Model → оценка
   LLM обновляется, чтобы получать более высокие оценки
```

### DPO (Direct Preference Optimization)

Более простой подход (2023):

```
1. SFT (как в RLHF)

2. DPO:
   Датасет: сравнения (тот же)
   → математическая формула, которая обновляет LLM напрямую
   → без отдельной Reward Model
   → без RL
```

### Сравнение

| Аспект | RLHF | DPO |
|--------|------|-----|
| Компонентов | 3 (SFT + RM + RL) | 2 (SFT + DPO) |
| Сложность | Высокая (PPO нестабилен) | Низкая |
| Качество | Выше (эталон) | 90-95% от RLHF |
| Данные | Сравнения | Сравнения |
| Вычислительно | Дорого | Дёшево |

**Когда что:**

```
RLHF:
  - Критическое качество (production)
  - Есть команда RL-инженеров
  - Бюджет позволяет

DPO:
  - Хорошее качество (достаточно для большинства задач)
  - Маленькая команда
  - Быстрый эксперимент
```

## 4. Fine-tuning vs Prompting vs RAG — decision framework

```
Вопрос 1: Нужны ли новые знания?
  │
  ├── Да → RAG (данные меняются) или Fine-tuning (статические данные)
  │
  └── Нет → Вопрос 2

Вопрос 2: Текущая модель даёт правильный, но не в том формате ответ?
  │
  ├── Да → Fine-tuning (стиль, формат, тон)
  │
  └── Нет → Вопрос 3

Вопрос 3: Проблема решается хорошим промптом?
  │
  ├── Да → Prompt Engineering
  │
  └── Нет → Fine-tuning или смена модели
```

### Матрица выбора

| Условие | Prompting | RAG | Fine-tuning |
|---------|-----------|-----|-------------|
| Быстрое решение | ✅ | ❌ (нужна инфра) | ❌ (нужны данные) |
| Меняющиеся данные | ❌ (контекст) | ✅ | ❌ |
| Специфический формат | ❌ (нестабильно) | ❌ | ✅ |
| Нет данных для FT | ✅ | ✅ | ❌ |
| Дёшево | ✅ | Средне | Дорого |
| Контроль поведения | Средний | Низкий | Высокий |
| Новые знания | ❌ | ✅ | Ограниченно |

## 5. Cost fine-tuning

### Что нужно для fine-tuning

```
Минимальный датасет: 500-1000 примеров
Хороший датасет: 5000+ примеров
Формат: JSONL (prompt + completion)

Пример:
{"prompt": "Переведи на английский: Привет, как дела?",
 "completion": "Hello, how are you?"}

Стоимость:
  LoRA 7B:    ~$10-50  (1 час на 1 GPU)
  LoRA 70B:   ~$100-500 (1 день на 4 GPU)
  Full FT 7B: ~$200-1000 (1 день на 8 GPU)
```

### Когда fine-tuning окупается

```
Monthly API cost > $10,000 → fine-tuning может окупиться
  - Дешевле инференс через свой адаптер
  - Меньше токенов на промпт (не нужно few-shot)
  - Выше скорость (меньше контекст)

Monthly API cost < $1,000 → fine-tuning НЕ окупится
  - Prompt engineering даст 90% результата
  - RAG решит проблему знаний
  - Fine-tuning — лишняя сложность
```

### Data Quality — качество данных решает всё

Успех fine-tuning на 80% зависит от данных и только на 20% — от архитектуры и гиперпараметров.

**Качество > количество:**
500 хорошо размеченных примеров дадут лучший результат, чем 5000 шумных. Каждый пример должен быть проверен человеком или LLM-жури.

**Дедупликация:**
- Удаляй near-duplicate примеры (совпадение n-gram > 80%)
- Используй embedding similarity (cosine > 0.95) для поиска дублей
- Оставляй только один представитель на группу语义чески идентичных примеров

**Очистка данных:**
- Удали примеры с неправильным форматированием (битые JSON, лишние пробелы)
- Проверь на противоречия — одинаковый prompt не должен вести к разным completion
- Отфильтруй примеры, где эталонный ответ содержит фактические ошибки

**Сбалансированный датасет:**
- Обеспечь равное покрытие всех целевых сценариев
- Если один класс составляет 80% данных — модель переобучится на него
- Используй стратифицированную выборку при разбиении

**Разбиение для кросс-валидации:**
80/10/10 — train/val/test. Валидационная выборка используется для early stopping и выбора гиперпараметров. Тестовая — только для финальной оценки, ни разу не смотри на неё во время обучения.

## Итоги

```
Fine-tuning:
  LoRA/QLoRA — дешёвый entry point (6-12 GB VRAM)
  Data quality > data quantity (500 хороших примеров > 5000 плохих)
  
RLHF vs DPO:
  RLHF — золотой стандарт, но сложный
  DPO — 90% качества за 10% усилий

Выбор подхода:
  Новые знания → RAG
  Формат/стиль → Fine-tuning
  Быстрый эксперимент → Prompting
```
