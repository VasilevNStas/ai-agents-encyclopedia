# Модуль 5: RAG 2.0

> [!quote] Ключевая идея
> RAG — это способ дать LLM актуальную информацию, которую она
> не могла знать в момент обучения. Без RAG любая LLM — это
> энциклопедия 2023 года.
> RAG (Retrieval-Augmented Generation, или «поисковая дополненная генерация») — это ==технология, которая объединяет большие языковые модели (LLM) с внешними базами знаний для повышения точности ответов==. Вместо того чтобы полагаться только на запомненные данные, ИИ сначала ищет релевантную информацию в документах, интернете или базах данных, а затем генерирует ответ на их основе

---

## 1. Chunking

Разбиение документов на фрагменты перед индексацией.

| Стратегия | Как работает | Когда |
|-----------|-------------|-------|
| **Fixed-size** | Режем по N токенов | Быстро, но режет смысл |
| **Semantic** | Режем по границам абзацев/предложений | Лучшее качество |
| **Recursive** | Пробуем большой размер → уменьшаем | Универсально |
| **Agentic** | LLM решает, где резать | Максимум качества |

**Best practice:** Начинай с semantic chunking (256-512 токенов), тестируй качество retrieval.

### Chunk Overlap (перекрытие фрагментов)

При разбиении документа полезно добавлять перекрытие между соседними фрагментами — несколько токенов из конца одного фрагмента попадают в начало следующего.

**Зачем нужно:**
- Сохраняет контекстную непрерывность — предложения и абзацы не обрываются на границе чанков
- Предотвращает потерю сущностей, которые пересекают границу фрагмента (имена, даты, термины)

**Типичные значения:** 10-20% от размера чанка (50-100 токенов для чанка в 512 токенов).

**Компромиссы:**
- Больше перекрытие → выше вероятность найти полный контекст → лучше retrieval
- Больше перекрытие → больше всего токенов в индексе → дороже хранение и поиск

**Best practice:** 64-128 токенов перекрытия для чанков по 512 токенов. Это даёт хороший баланс качества и стоимости.

## 2. Embedding

Текст → вектор чисел. Семантически близкие тексты — близкие векторы.

```python
# Упрощённо:
text = "Столица Франции — Париж"
vector = embed(text)  # → [0.23, -0.45, 0.78, ..., 0.12] (1024 числа)

query = "Какой город является столицей Франции?"
query_vector = embed(query)

# Косинусная близость: чем ближе к 1, тем релевантнее
similarity = cosine_similarity(vector, query_vector)  # 0.92
```

### Модели embedding

| Модель | Размерность | Сильные стороны |
|--------|-------------|-----------------|
| text-embedding-3-small | 512/1536 | OpenAI, дёшево |
| text-embedding-3-large | 256/1024/3072 | OpenAI, качество |
| voyage-2 | 1024/1536 | Voyage AI, мультиязык |

## 3. Retrieval

### Dense Search

Поиск по embedding-векторам. Хорош для семантики, плох для точных совпадений.

```
Запрос: «iPhone 15 цена» → ищет ближайшие векторы
Найдёт: «Сколько стоит iPhone 15», «Цена на iPhone 15 в России»
Не найдёт: «iPhone 15 79990 руб» (если embedding не captures точную сумму)
```

### Sparse Search (BM25)

Поиск по ключевым словам. Хорош для точных терминов, плох для семантики.

```
Запрос: «iPhone 15 цена» → ищет слова "iPhone", "15", "цена"
Найдёт: любой документ с этими словами
Не найдёт: «Сколько стоит телефон пятнадцатой модели»
```

### Hybrid Search (лучшее из двух)

Взвешенная комбинация dense + sparse с RRF (Reciprocal Rank Fusion).

```
score = α × dense_score + (1-α) × sparse_score
// α обычно 0.5-0.7
```

### Knowledge Graph Retrieval (графовый поиск)

Вместо поиска по плоским фрагментам текста, графовый подход ищет по графу сущностей и их связей.

**Как работает:** документы парсятся в триплеты (субъект — отношение — объект), формируется граф знаний. Поиск идёт по узлам и рёбрам, а не по векторной близости.

**Когда использовать:**
- Данные с богатыми связями: продукты и их характеристики, люди и компании, научные статьи и цитирования
- Сценарии, где важно не просто найти текст, а понять, как сущности связаны
- Комбинированные вопросы: «Какие продукты компании X выпущены после 2024 года?»

**Инструменты:**
- **GraphRAG** (Microsoft) — автоматическое построение графа из документов
- **Neo4j** — графовая БД с векторными индексами
- **LlamaIndex KG Integration** — построение графа и retrieval через LlamaIndex

## 4. Reranking

Уточнение результатов после retrieval.

```
Top-20 от retrieval → Reranker → Top-5
```

Reranker (cross-encoder) — более тяжёлая модель, которая смотрит на пару (запрос, документ) целиком и даёт точную оценку релевантности.

---

## 5. RAG-aware Prompting

Как писать промт для RAG-системы:

```
Ты отвечаешь на вопрос, используя ТОЛЬКО предоставленные контексты.
Если контекст не содержит ответа — скажи «Я не могу найти эту информацию
в предоставленных документах».

Контексты:
{contexts}

Вопрос: {question}

Цитируй источники: [source:N]
```

### Anti-patterns RAG

- LLM игнорирует контекст и использует свои знания
- Слишком много контекстов (шум > сигнал)
- Нет цитирования источников

## 6. Пример кода: минимальный RAG-пайплайн

Полноценный RAG требует векторную БД (Chroma, Qdrant, Pinecone) и embedding модель. Ниже — концептуальный пример с numpy, чтобы понять логику.

```python
import numpy as np

# 1. Чанкинг — разбиваем документ на фрагменты
documents = [
    "Столица Франции — Париж. Население — 2.1 млн.",
    "Париж известен Эйфелевой башней, Лувром и Монмартром.",
    "Франция — член Евросоюза. Валюта — евро.",
    "В Лувре хранится Мона Лиза Леонардо да Винчи.",
]

# 2. Эмбеддинги (упрощённо: TF-IDF как векторы)
# В реальности — text-embedding-3-small / voyage-2 / intfloat-multilingual
vocab = ["столица", "франция", "париж", "эйфелев", "лувр", "евро"]

def simple_embed(text):
    vec = np.zeros(len(vocab))
    for i, word in enumerate(vocab):
        if word in text.lower():
            vec[i] = 1.0
    return vec

chunk_vectors = np.array([simple_embed(d) for d in documents])

# 3. Retrieval — косинусная близость
query = "Где находится Мона Лиза?"
query_vec = simple_embed(query)
scores = chunk_vectors @ query_vec / (
    np.linalg.norm(chunk_vectors, axis=1) * np.linalg.norm(query_vec) + 1e-8
)
top_idx = np.argsort(scores)[-2:][::-1]  # Top-2

contexts = [documents[i] for i in top_idx]

# 4. RAG-aware промт
rag_prompt = f"""
Ответь на вопрос, используя ТОЛЬКО контекст ниже.

Контекст:
{chr(10).join(f'- {c}' for c in contexts)}

Вопрос: {query}

Если контекст не содержит ответа — скажи: «Нет информации».
Цитируй источники: [doc:N]
"""
print(rag_prompt)
# Вывод: ответ будет про Лувр (doc 3) и Париж (doc 1)
```

**На практике** вместо `simple_embed` используются:
- `sentence-transformers` (локально)
- `openai.embeddings.create` (API)
- `voyageai` (API, лучший для русского языка)

А вместо numpy-поиска — векторные БД: Chroma, Qdrant (in-memory), Pinecone (облачная).

## Практика

> [!tip] Задание: RAG-пайплайн для своей базы знаний
>
> Собери минимальный RAG-пайплайн для документов, с которыми ты работаешь.

**Шаг 1. Подготовь данные**
Возьми 3-5 документов по одной теме. Разбей на фрагменты по 256-512 токенов — semantic или fixed-size chunking.

**Шаг 2. Выбери embedding**
`sentence-transformers` (локально), `text-embedding-3-small` (OpenAI) или `voyage-2` (лучший для русского). Построй вектор для каждого фрагмента.

**Шаг 3. Проиндексируй**
Chroma, Qdrant in-memory, или numpy-массив с косинусной близостью.

**Шаг 4. Напиши RAG-aware промт**
По шаблону из модуля. Запрети LLM использовать собственные знания.

**Шаг 5. Протестируй**
3 вопроса, на которые отвечают твои документы + 1 вопрос без ответа в документах. Проверь:
- Нашёлся ли правильный контекст?
- Сказала ли LLM «не знаю» на вопрос без контекста?
- Есть ли цитирование источников?

**Вопросы для самоанализа:**
- Какие фрагменты возвращались нерелевантными? Почему?
- Где LLM проигнорировала контекст?
- Что быстрее: dense / sparse / hybrid search на твоих данных?
