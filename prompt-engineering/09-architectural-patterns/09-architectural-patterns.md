# Модуль 9: Архитектурные паттерны

> [!quote] Ключевая идея
> Один агент — это tool. Несколько агентов — это архитектура.
> Паттерны — это проверенные способы организовать их совместную работу.

---

## 1. Multi-Agent Архитектуры

### Supervisor + Workers

```
        ┌────────────┐
        │ Supervisor │  — распределяет задачи, собирает результаты
        └─────┬──────┘
        ┌─────┼─────┐
        │     │     │
   ┌───-─▼┐┌─▼──┐ ┌▼────┐
   │Worker││ Wrk│ │ Wrk │  — каждый решает свою подзадачу
   └──────┘└────┘ └─────┘
```

**Когда:** Большая задача, которая делится на независимые части.

**Промт Supervisor:**
```
Ты — supervisor. У тебя есть workers:
- researcher(query) — ищет информацию
- analyzer(data) — анализирует
- formatter(content) — оформляет

Раздели задачу на подзадачи и распредели между workers.
Собери результаты в один ответ.
```

### Evaluator Pattern

Generator + Evaluator: один агент создаёт ответ, второй проверяет его качество. Если качество ниже порога — генератор дорабатывает.

```
        ┌──────────┐
   ┌───►│ Generator│───► черновик
   │    └──────────┘
   │         │
   │         ▼
   │    ┌──────────┐
   └────┤ Evaluator│  — проверяет качество
        └──────────┘
```

**Когда:** Задачи, где качество важнее скорости (код, контент, юридические документы). Работает только если критерии качества можно формализовать.

```
        ┌──────────┐
   ┌───►│ Generator│───► response
   │    └──────────┘
   │         │
   │         ▼
   │    ┌──────────┐
   └────┤ Evaluator│  — проверяет, достаточно ли качества
        └──────────┘
```

**Когда:** Задачи, где качество важнее скорости (код, контент).

## 2. Orchestration Patterns

Оркестратор — центральный компонент, который принимает задачу, разбивает её на подзадачи, распределяет между агентами и собирает результат. Это «менеджер проекта» для агентов.

### Sequential (конвейер)

```
A → B → C → D
```

Каждый шаг получает результат предыдущего.

**Когда:** Задачи с жёсткой последовательностью (обработка данных: извлечь → очистить → сохранить).

### Parallel (параллельно)

```
      ┌─→ B1 ─┐
A ────┤─→ B2 ─├───→ C
      └─→ B3 ─┘
```

Задача A делится на независимые подзадачи, которые выполняются параллельно.

**Когда:** Анализ с разных точек зрения, поиск по разным источникам.

### Map-Reduce

```
        ┌─→ chunk1 ─┐
docs ───┤─→ chunk2 ─├──→ merge ─→ ответ
        └─→ chunk3 ─┘
```

Разбить на части → обработать каждую → собрать.

**Когда:** Огромные документы, которые не влезают в контекст.

### Routing

```
       ┌─→ payments
вход ──┼─→ support
       └─→ sales
```

Маршрутизация запроса к нужному агенту на основе классификации.

**Когда:** Система с разными доменами (пишется запрос к нужной команде).

## 3. Reflection Pattern

Агент проверяет и улучшает свой ответ.

```
Цикл:
1. Generator: пишет ответ
2. Evaluator: оценивает ответ (critique)
3. Generator: улучшает ответ на основе critique
4. Повторять до прохождения порога качества
```

**Промт для рефлексии:**
```
Ты — критик. Оцени ответ по критериям:
- Полнота (0-10)
- Точность (0-10)
- Ясность (0-10)

Если хотя бы один < 7 — напиши, что нужно улучшить.
Если все >= 7 — ответь APPROVED.
```

## 4. LLM Wiki

Долговременная память через генерируемые документы.

```
Запрос → LLM генерирует wiki-страницу → сохраняет
Новый запрос → LLM читает wiki + отвечает
```

**Когда:** Агент, который учится на своей работе и помнит между сессиями.

**Пример:** Ассистент по кодовой базе запоминает архитектуру проекта.

---

## 5. Event-Driven Agents

Агенты, которые реагируют на события (не на прямые запросы).

```
Событие: новый issue в GitHub
  → Agent: анализирует issue
  → Agent: классифицирует (bug/feature/question)
  → Agent: назначает assignee
  → Agent: пишет первый комментарий
```

**Когда:** Фоновые процессы, CI/CD, мониторинг.

**Выбери сценарий:**

- Code review агент (анализ + тесты + документация)

**Опиши:**

4. Где нужна рефлексия / проверка качества
